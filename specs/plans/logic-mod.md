# C# 逻辑 Mod 接入规划

状态：草案（初步构思稿）；2026-11-07整理。本文仅用于讨论方向与评估范围，尚未形成已确认的设计决策或实施承诺；项目划分、接口、协议、分期与验收均待后续设计和验证。方案以《杀戮尖塔 2》本地代码设计为主要参考，不表示插件加载、Harmony 支持或存档环境校验已经实现，也不自动改变现有玩法和协议。

## 目标与取舍

采用“轻量 C# 加载器 + 领域原生扩展 + Harmony”的结构：新增常规玩法优先进入游戏自身的领域模型、生命周期和状态管理；改变既有流程或介入未开放行为时使用 Harmony。优先减少对主线开发的影响，不提前建设完整规则 SDK，不为保持补丁目标而冻结内部实现或增加兼容分支。

宿主负责加载、运行环境记录、诊断和恢复入口；Mod 作者负责修改逻辑的正确性、多 Mod 适配和随游戏构建更新补丁。能够加载不等于玩法正确，示例插件和第三方完成度声明不作为验收结论。

主线继续直接维护领域规则，不依靠 Harmony 组织自身功能，也不复制第三方补丁实现。加载底座可先交付；原生扩展按实际领域需求逐步建立，原版实现与 Mod 共用执行路径，避免把“所有逻辑都靠方法补丁”作为最终形态。

本规划针对逻辑 Mod。数据与资源继续遵循现有[内容管线](../../docs/client-content.md)；受约束的事件内容创作与任意 C# 插件执行是不同能力，互不作为首批实施前提。

## 参考设计与适用边界

以下是对本地参考代码的观察，不是对其全部版本、运行正确性或维护成本的保证。本地来源为 `sts2`，不把参考工程或游戏资源作为本仓库依赖。

| 参考入口 | 本地代码中的行为 | 本项目选择 |
| --- | --- | --- |
| `src/Core/Modding/ModManager.cs` | 启动时发现 PCK、加载同名 DLL；调用标记的初始化入口，否则执行 Harmony `PatchAll` | 借鉴集中加载与初始化分支；纯逻辑插件不要求 PCK |
| `src/Core/Helpers/OneTimeInitialization.cs` | 设置读取后加载 Mod，随后初始化本地化、模型和模型 ID | 在会话、规则编译及相关缓存建立前加载 |
| `src/Core/Modding/ModSettings.cs`及 Mod 管理界面 | 保存启停状态，变更提示重启；初始化完成后不运行中加载 | 固定进程插件组合，重启后生效 |
| `src/Core/Saves/UserDataPathProvider.cs` | Mod 模式使用独立的 profile 目录 | 区分原版与 Mod 自动存档，文件自身记录运行环境 |
| `src/Core/Models/ModelDb.cs`、`src/Core/Helpers/ReflectionHelper.cs` | 将插件中的模型子类纳入模型数据库 | 区分类型发现、对象注册和实际玩法准入，不以扫描到类型代表接入完成 |
| `src/Core/Modding/ModHelper.cs`、`src/Core/Models/CardPoolModel.cs` | `AddModelToPool` 注册模型，内容池合并原版与 Mod 模型，首次生成后冻结注册 | 领域注册在会话规则及相关缓存建立前完成，确定组合后冻结 |
| `src/Core/Models/AbstractModel.cs`、`src/Core/Hooks/Hook.cs` | 模型提供攻击、抽牌、战斗等虚方法，宿主遍历监听模型调用行为 | 复用有领域语义的生命周期，原版与 Mod 经同一路径执行；不照搬卡牌模型或建立全 Core 钩子体系 |
| `src/Core/Models/ModelId.cs`、`src/Core/Saves/Runs/SavedPropertyAttribute.cs`、`SavedProperties.cs`、`SavedPropertiesTypeCache.cs` | 模型身份与受支持类型的实例属性保存；属性缓存提供 `InjectTypeIntoCache` 入口 | 逻辑类型身份与实例状态分离；状态类型、注册和恢复边界必须明确，不照搬反射属性存档 |
| `src/Core/Modding/ModManager.cs`、`src/Core/Localization/LocManager.cs` | 加载 PCK，并按插件目录约定合并本地化表 | 资源与本地化作为后续接入能力，不要求纯逻辑 Mod 制作 PCK |
| `src/Core/Multiplayer/Serialization/MessageTypes.cs`、`ModelIdSerializationCache.cs`、`src/Core/Multiplayer/Game/JoinFlow.cs` | 发现插件消息类型，模型 ID 映射纳入插件模型，连接时检查 Mod 列表与模型数据库哈希 | 借鉴运行环境与类型身份检查，不把联机扩展纳入本规划首批范围 |

这些能力分属两类：初始化标记、`ModHelper` 及插件类型发现是明确的 Mod 接线；模型基类、行为钩子和实例保存结构同时服务于原版玩法，Mod 可复用。公共可访问不等于长期兼容承诺，也不能由本地代码推断官方对所有结构的支持政策。

模型进入 `ModelDb` 不等于进入生成池、选择列表或其他消费者。本地版本仍有显式枚举的目录；新增模型须逐项检查实际准入路径。`SavedProperty` 也只支持特定类型及属性缓存注册，不意味着任意插件字段自动保存或自动满足网络序列化要求。

伴侣插件仅用于比较内部访问、方法替换、配置和状态处理的具体做法，不作为设计基准、产品实现来源或默认验收样本。Harmony 本身的运行时限制参考[官方补丁说明](https://harmony.pardeike.net/v2/articles/patching.html)。

## 插件包与初始化协议

纯逻辑插件采用普通目录，建议结构如下；名称与字段属于拟议契约：

```text
mods/
  ExampleMod/
    mod.json
    ExampleMod.dll
    dependencies/
```

| 清单字段 | 语义 |
| --- | --- |
| `id`、`name`、`version`、`author`、`description` | 唯一身份、版本与展示信息；身份使用英文命名空间 |
| `assembly` | 相对插件目录的入口程序集路径 |
| `hostApiVersion` | 加载协议版本，不代表 Core 内部 API 稳定 |
| `supportedGameBuilds` | 作者声明支持的游戏构建；首版按明确匹配校验 |
| `dependencies`、`loadAfter` | 必需依赖及先后关系；循环或矛盾拒绝加载 |

启动时先读取全部清单，检查路径、身份、版本与依赖，再得到确定的加载顺序。不依赖文件系统枚举顺序；无先后约束时使用稳定 ID 排序。

初始化采用两种互斥分支：

1. 存在 `ModInitializer` 标记时，调用唯一、签名符合契约的静态入口，由作者组织注册与补丁。多个或无效入口直接报错。
2. 没有标记时，宿主以 Mod ID 创建 Harmony 实例并调用该插件程序集的 `PatchAll`。

自定义初始化分支不再自动执行 `PatchAll`。入口接收简短的 `ModContext`，提供插件 ID、目录、日志、宿主构建及当前插件的固定配置，不扩展成通用世界修改接口。后续原生扩展可以通过明确的注册入口接入；初始化仅登记实现与契约，不创建或修改尚未建立的会话世界。

## 工程职责与加载生命周期

建议新增两个小项目，最终名称在实施时确定：

| 项目或层次 | 职责 |
| --- | --- |
| `San9.Mod.Abstractions` | 初始化标记、上下文和加载协议公共类型；不依赖 Godot |
| `San9.Mod.Hosting` | 清单、发现、依赖排序、程序集加载、Harmony 接线和诊断 |
| Application | 接收确定的运行环境及领域注册结果，组织会话、规则组合、配置及存档校验 |
| Core | 继续持有领域状态、规则及领域扩展执行语义，不依赖 Hosting、磁盘目录、Godot 或 Harmony |
| Client.Godot 与 Headless | 使用同一 Hosting 能力，在各自启动流程接入 |

游戏设置读取后、会话创建和规则编译前完成加载。补丁应在目标代码执行或相关预热之前安装；仍需在实际发布运行时验证效果。原生扩展接入后，启动流程为“发现与校验 → 插件初始化与登记 → 注册结果校验并冻结 → 会话规则组合 → 世界创建或恢复”；禁止在依赖注册结果的缓存建立后继续追加类型。

插件共享宿主的游戏程序集、公共契约和 Harmony，避免把同一契约加载成不同类型身份。首版不承诺插件私有依赖的任意版本并存；程序集身份冲突应明确报告，不静默选择。采用简单共享加载上下文，不建设可卸载的隔离运行时。

Mod 作者可以引用对应构建的游戏程序集，使用公共成员、反射及 Harmony。主线不全面公开内部类，也不增加面向所有插件的友元访问；不得借用测试程序集身份作为正式接入方法。

Harmony 作用于整个进程。加载顺序与插件组合一经确定，本进程内所有会话一致；启停、更新或改变组合均须重启，不支持热加载、卸载及同进程多套补丁环境。

## 加载状态、失败与诊断

分别记录发现、停用、校验通过、初始化成功和失败，不把程序集已加载等同于插件初始化成功。

清单和依赖错误在执行插件代码前集中报告。开始执行插件代码后发生初始化失败，终止本次启动，提供日志和 `--no-mods` 恢复入口；不自动在当前进程退回原版继续运行。程序集、静态初始化与部分补丁可能已经生效，捕获异常不能证明已回滚。

日志记录游戏构建、Harmony 版本、插件身份和顺序、初始化结果、异常及可追踪的补丁归属。不吞掉初始化失败，不承诺自动解决任意补丁之间的语义冲突。

插件属于受信任的进程内代码，不提供权限沙箱。Mod 模式需在界面和诊断中可识别；原版问题复现可以通过 `--no-mods` 建立独立基线，不因此认定所有 Mod 模式问题均由插件导致。

## 运行环境、配置与存档

Mod 模式的自动存档使用独立目录，手动存档保留文件选择能力并携带环境标记。目录隔离不能代替文件内的环境检查。

存档和显式命令脚本所用日志记录相同的运行环境描述：

- 游戏构建和适用的宿主协议版本。
- 启用的 Mod ID、版本、实际代码及插件自带依赖指纹、确定的加载顺序。
- 影响玩法的配置及其指纹。

原版环境显式表达为空插件集合。恢复时先核对再创建执行会话；缺失插件或环境不匹配时明确拒绝正常恢复，不隐式迁移或补值。环境指纹用于识别输入，不证明插件行为确定或可信。

提供统一配置读取与保存位置。影响玩法的配置在会话建立时形成不可变快照，各次查询、预览、AI 与结算消费同一份配置。显示配置可即时变化；以后需要局内修改玩法配置时，再设计显式会话操作，不通过静态全局值绕过会话。

以上是拟议协议变化，实施时需同步[SessionProtocol](../../src/San9.Application/SessionProtocol.cs)、保存与命令日志消费者及校验器。录像已延期，不增加完整重放要求。

## 状态与原生扩展边界

原生扩展是整体方案的一部分，首批仅先以不新增持久状态的规则修改打通加载闭环。后续选取一个真实领域需求，贯通身份、注册、实际准入、执行和恢复，而不是先列出一套覆盖全部玩法的抽象基类。

### 注册与身份

定义稳定的命名空间身份，明确行为实现、内容定义与运行时实例的对应关系。存档中的身份不得依赖程序集限定类型名；同一身份的重复注册必须报错。类型发现、注册成功和在当前世界可用是不同状态，查询、AI、命令及恢复均须核对相应消费者。

领域契约放在对应的领域边界，不把加载协议程序集扩张为全部玩法类型的集合。Application 组合已登记实现与会话内容；Core 决定执行语义及不变量。首个扩展点应从实际需求抽取，原版实现与插件实现使用同一契约。

### 生命周期与行为

常规新增玩法通过已开放的领域能力运行，例如事件的资格、触发、待答和结算，或持续任务的开始、推进、取消和完成。只有选定实际需求后才定义具体契约，不把这些示例视为已承诺首批全部支持。

每个入口明确调用时机、作用对象、顺序、查询与执行权限、随机来源、失败处理及暂停恢复位置。区分可组合监听与独占规则替换；不能通过一个全局优先级解决所有语义冲突。正式执行、查询预览与 AI 应共享对应规则。Harmony 用于改变既有流程或介入原生契约之外的行为，不作为新增对象进入生命周期的唯一途径。

### 实例状态与持久化

Harmony 能改变方法，但不会自动解决持久状态、事务与分支问题。游戏已有状态模型能完整表达时优先复用，不为每个 Mod 另造状态仓库。

现有[模拟引擎](../../src/San9.Core/Simulation/SimulationEngine.cs)的 `Fork()` 共享规则对象。新增玩法进度不能仅存在于插件静态字段、共享规则实例或外部文件；实际需要时再提供由世界持有、随事务提交、分支隔离、存读档及确定性校验的 Mod 状态机制。调用期间的临时上下文与跨操作的权威状态须明确区分。

需要新增状态时，定义注册类型或状态格式、版本、实例归属、引用校验和恢复过程，明确允许保存的值；不承诺任意 CLR 对象图自动序列化。首次提供有状态原生扩展时，这些能力必须随同交付，不能把状态支持拆成后续补齐项。

这一能力未完成前，不宣称已支持任意新玩法。改变公式也可能让世界不变量或存档校验失效，作者仍须核对受影响的规则、查询与恢复路径。第一批不建设通用任务、待答、命令、UI 和世界修改框架，也不固定所有内部结算阶段为长期公共契约。

## 分期与验收

| 阶段 | 交付范围 |
| --- | --- |
| 第一批：逻辑 Mod 基础 | 清单、确定加载顺序、初始化入口、Harmony、客户端与 Headless 接线、日志、`--no-mods`、固定玩法配置、运行环境记录和恢复校验 |
| 原生领域扩展闭环：按真实需求启动 | 选取一个领域扩展，贯通稳定身份、注册与冻结、玩法准入、生命周期、查询与执行；涉及新增状态时同时完成事务、分支和存读档 |
| 管理体验：独立推进 | Mod 列表、启停、详情、失败信息和重启提示，复用第一批配置与加载状态；不作为领域扩展前提 |
| 后续按需扩展 | 更多领域注册接口、资源包、本地化及分发平台 |

首批使用独立自制示例，至少一个自动补丁插件和一个自定义初始化插件。不依赖原版资源或第三方插件完成默认测试。

- [ ] 无 Mod 时沿用现有规则行为；原版环境记录正确。
- [ ] 真实 DLL 在客户端与 Headless 中都能修改同一条规则，初始化时机一致。
- [ ] 加载顺序不随目录枚举顺序变化；重复身份、缺依赖、循环和程序集冲突明确报告。
- [ ] 初始化失败后不进入游戏；`--no-mods` 能在新进程启动原版环境。
- [ ] 配置在会话内固定，查询、预览、AI 和正式结算使用同一逻辑环境。
- [ ] 相同环境下分支计算互不污染，存读档及显式命令脚本验证结果一致；环境不匹配在执行前拒绝。
- [ ] 实际导出包可加载并应用补丁，确认目标平台、Harmony 版本、依赖和裁剪策略；开发构建通过不替代发布验证。
- [ ] 按[测试职责](../../tests/README.md)运行 `dotnet test San9Remake.slnx` 与 `dotnet test tests/San9.Headless.Tests/San9.Headless.Tests.csproj`；管理界面画面验收遵从用户分工。

原生领域扩展的首个闭环另须满足：

- [ ] 自制插件通过领域注册加入实际玩法，使用原生行为契约执行，不依赖 Harmony 修改该契约的宿主调用点。
- [ ] 发现类型、登记实现及进入候选／执行流程分别验证；重复身份和冻结后注册被拒绝。
- [ ] 原版与插件实现经相同生命周期运行；相关查询、预览、AI 和提交使用同一规则组合。
- [ ] 涉及新增状态时，分支计算互不污染、失败不提交部分状态、存读档恢复实例身份及进度，未知身份与无效引用明确报错。

动态程序集加载与当前 Release 部分裁剪组合需要专门验证，参考[微软裁剪限制说明](https://learn.microsoft.com/en-us/dotnet/core/deploying/trimming/incompatibilities)。不把当前保留游戏程序集视为第三方插件依赖已经完整保留。
